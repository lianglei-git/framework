# 数据层结构规范：迁移与表设计

数据层的不可逆资产是**表结构**——组件重构只是改代码，schema 变更牵扯存量数据。
因此本领域的铁律只有一条，其余都是它的推论：

## 铁律：迁移只增不改（append-only）

- 已执行过的 migration 文件**永远不许编辑**，一个字符都不许动。
- 写错了怎么办：**fix-forward**——写一个新的 migration 去纠正，错误的那份留在历史里。
- 理由：migration 历史是数据库的 git log，改历史意味着不同环境（本地/测试/生产）
  执行过的内容不再一致，从此没人说得清任何一个库的真实状态。

## 迁移文件规范

- 位置与命名：`migrations/YYYYMMDDHHMM_<动词>_<对象>.sql`
  （如 `202607221030_create_wordbook.sql`、`202607231400_add_source_to_wordbook.sql`）。
- **一个文件只做一件事**：建一张表、加一列、建一个索引。禁止一份文件里混多个意图，
  否则失败时无法定位执行到哪一步。
- **schema 变更与数据回填分离**：改结构是一份 migration，灌数据/刷存量是另一份。
- 文件头部注释必填：

```sql
-- feat:        FEAT-xxx（对应需求 id）
-- purpose:     一句话说明
-- reversible:  yes | no（删列、改类型等不可逆操作必须标 no）
-- destructive: yes | no（是否触碰存量数据）
```

## 表设计约定

- 命名：表与字段一律 snake_case；禁止缩写到看不懂（`usr_wd_rel` 不行）。
- 每张表必备：`id`（主键）、`created_at`、`updated_at`。
- 每张表有唯一归属业务（owner），记入 `schema.llms.txt`；
  跨业务需要读同一份数据时走 service 层，不允许业务 B 直接写业务 A 的表。
- 给既有表加列：必须可空或带默认值——对大表加 NOT NULL 无默认列会锁表且使旧代码即刻报错。

## 变更的两级分类（后续所有流程按此分级）

| 级别 | 包含 | 风险 |
|------|------|------|
| 加法变更 | 建新表、加可空/带默认的列、加索引 | 低：旧代码无感知 |
| 破坏性变更 | 删表、删列、改列名、改类型、删索引 | 高：不可逆或牵扯存量数据 |
