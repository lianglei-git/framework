# 需求文档规范（REQUIREMENT.md）

需求层的不可逆资产是**已确认的范围决策**（尤其 Non-goals）。本规范定义它的载体。

## 落位与命名

- 项目内位置：`docs/requirements/<FEAT-id>-<短名>/REQUIREMENT.md`，一需求一文件夹。
- 调研材料、原型图等附件放同文件夹内，不混入正文。
- `FEAT-id` 全局唯一、只增不复用（`FEAT-001`、`FEAT-002`…），废弃的 id 不回收。

## 生命周期

```
draft ──(人确认)──> confirmed ──> in-dev ──> shipped ──> deprecated
```

- `draft`：agent 可自由起草和修改。
- `confirmed`：**人拍板后进入**。此后对范围（In Scope / Non-goals / 验收标准）的
  任何改动都是 L5 决策，且必须在决策记录留痕。
- 状态只能沿箭头前进，唯一例外：任何状态可直接转 `deprecated`。

## 文档模板

```markdown
---
id: FEAT-001
title: 一句话标题
status: draft
owner: <拍板人>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

## 问题陈述（必填）
为「谁」解决「什么问题」。必须写问题，禁止写成功能描述。
（反例："做一个生词本功能"。正例："学习者查过的生词无处沉淀，复习时找不回来"。）

## 调研摘要（可选，发散阶段产物）
候选需求点清单的结论与来源链接。全文放附件，此处只留结论。

## In Scope（必填）
本期做什么，条目式。

## Non-goals（必填，≥1 条）
明确不做什么，每条带一句话原因。
这是本文档最值钱的字段：它是收敛动作的存档，也是开发时防范围蔓延的依据。
- 不做 X：因为……
- 不做 Y：本期资源不够，放到 FEAT-xxx 再议

## 验收标准（必填）
每条一个稳定 id，确认后 id 不变（内容变更走 L5）。
- AC-1: <主语> 能在 <条件> 下 <做什么>，结果是 <可观测的状态>
- AC-2: ...

## 依赖与影响（如有）
依赖的 API 契约 / 数据表 / 公共组件；对存量功能的影响。

## 决策记录
| 日期 | 决定 | 原因 |
|------|------|------|
```

## 验收标准（AC）的可判定性要求

每条 AC 必须能回答"怎么验证"——即可以直接翻译成一个测试用例。

- 结构：主语 + 动作 + 可观测结果（必要时加量化条件）。
- **禁用模糊词**：流畅、好看、快速、友好、易用、优化、提升、更好、体验佳。
  出现即视为不可判定，打回重写（改成"首屏可交互 < 2s"这类可观测语句）。
- AC 是需求层与测试的枢纽：开发任务的终止条件包含"每条 AC 有对应测试且通过"。
