# 后端结构规范

后端的不可逆资产是 **API 契约**——一旦有前端/移动端依赖，改动就是半不可逆的。
代码内部怎么重构都便宜，契约一动就有连锁反应，所以治理重心全在边界上。

## 分层（单向依赖，由 L2 强制）

```
router → handler → service → repository → (DB)
```

| 层 | 职责 | 禁止 |
|----|------|------|
| router | 只做路由注册与中间件挂载 | 任何逻辑 |
| handler | 解析/校验请求、调 service、组装响应 | 业务逻辑、直接访问 repository/DB |
| service | 业务逻辑的唯一所在地 | 出现任何 HTTP 概念（status code、request 对象） |
| repository | 数据访问的唯一所在地（ORM/SQL） | 业务判断 |

- 依赖只准向右，禁止跨层（handler 直接调 repository 是最常见的违规，L2 重点盯防）。
- **一个业务域一个包/模块**，内部各自四层；跨业务调用只准发生在 service 层之间。

## 错误处理约定

- service 层返回带业务错误码的 error，不感知 HTTP；
- handler 层统一把业务错误码翻译成 HTTP status + 响应体；
- 全项目一份错误码表（作为契约的一部分记入 `api.llms.txt`），禁止散落的裸字符串错误。

## 契约先行（本领域的核心工作方式）

- 任何端点，**先在 `api.llms.txt` 写契约条目，后写实现**。
- 契约是前后端的共同依据：前端 agent 对着它写调用与 mock，后端 agent 对着它写实现，
  两边并行，谁也不猜谁。
- 实现与契约不符时，以契约为准修实现；发现契约本身不合理，走变更流程改契约，
  禁止"代码先改了，契约回头再说"。

## 契约变更的两级分类（与数据层同构）

| 级别 | 包含 | 处理 |
|------|------|------|
| 加法变更 | 新端点、响应加字段、请求加**可选**字段 | 轻量确认后动手 |
| 破坏性变更 | 删端点/字段、改字段名/类型/语义、请求加必填字段、改错误码含义 | L5：呈报受影响消费方后等批准 |

破坏性变更获批后优先走「新旧并存 + 标记 deprecated + 消费方迁移完再删」，
直接原地改是最后手段。
